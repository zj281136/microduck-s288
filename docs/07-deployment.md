# 05 · 真机部署：先站一会儿，再迈第一步

终于轮到实物了。这一步先用仓库配套的 ONNX，不急着换模型或改增益。目标也放小一点：看清楚启动过程，完成一次短时零速度站立，再尝试可重复的低速前进。

开始前，你应该已经完成上一章的模型加载、电机反馈、零位和方向检查，IMU 的安装轴向也已经核对。标定文件属于眼前这台机器人；机械、固件或传感器还有没确认的地方，先把对应问题解决。

整机共有 15 个舵机，但当前 ONNX 和部署控制循环仅使用 14 个 RL 关节（ID 0–13）。第 15 个舵机（ID 14）不由本策略控制；不要将它追加到 14 维动作或 RL 标定模板中。

## 1. 把运行现场准备好

本篇命令都在**树莓派的 `software/deployment` 目录**执行：

```bash
cd software/deployment
.venv/bin/python deploy.py check
```

如果你已经在这个目录，不必再执行 `cd`。检查应显示 `[1,61]` 输入、`[1,14]` 输出、`position_source: rotor`，并通过内置模型的 manifest 哈希校验。这条命令不打开硬件。

确认本机标定文件存在：

```bash
ls -l teleop/scripts/microduck_s288_calibration.json
```

接下来让双脚接触地面，防坠保持松弛，使机器人能自己承重，同时在失去平衡时被接住。悬空状态与着地站立不同，不用悬空抖动来判断地面步态。

把动力切断放到触手可及的位置。程序退出会尝试撤去增益，鸭子这时不会继续主动站立；通信失效时，也不能只依赖软件停机。

## 2. 第一次只运行三秒策略

根据你的设备修改 `--port`。示例 IMU 地址为 `0x6a`：

```bash
.venv/bin/python deploy.py stand \
  --port /dev/ttyACM0 \
  --i2c-address 0x6a \
  --duration 3 \
  --stand-ramp-seconds 12 \
  --policy-ramp-seconds 3 \
  --vx 0 --vy 0 --wz 0 \
  --max-speed 5 --print-rate 1 \
  --arm-ground-test
```

`--arm-ground-test` 会显式启用真机运动，准备好支撑后再执行。这不是一次只看文件的检查。

程序先加载模型、校准 IMU，再过渡到站立目标，最后进入策略控制。IMU 校准期间扶正并保持静止。`--duration 3` 指策略阶段的三秒，前面的初始化和 12 秒站立过渡另算，所以启动三秒后没有退出是正常的。

第一次重点看过程：

- **站立过渡时**，关节是否朝预期方向运动，有没有某一侧顶住限位或明显偏斜。
- **策略接管时**，有没有突然跳变、连续抖动、脚掌异常打滑或明显倾倒。
- **退出时**，支撑是否稳妥接住机体，终端是否报告异常并给出日志位置。

这些现象都比“程序有没有报错”更有用。如果出现明显异常，结束测试，保存日志，回查标定、IMU、结构和反馈。不要连续重复同一个异常动作，或先提高阈值让它继续跑。

## 3. 看懂几个会用到的参数

| 参数 | 在本教程里的作用 |
| --- | --- |
| `--port` | 电机控制器设备，长期运行可换成 by-id 路径 |
| `--duration` | 策略阶段时长，示例先用短时间 |
| `--stand-ramp-seconds` | 从当前姿态向站立目标过渡的时间 |
| `--vx` / `--vy` / `--wz` | 前后速度、侧向速度、偏航角速度，单位分别为 m/s、m/s、rad/s |
| `--policy-ramp-seconds` | 固定指令入口中速度 command 的过渡时间 |
| `--max-speed` | 实测关节速度的停机阈值，单位 rad/s，不是行走速度上限 |
| `--print-rate` | 终端状态输出频率 |

这里的三秒 command 过渡不是把策略动作做低通。当前策略按训练匹配参数运行，不要为了“柔和一点”就另加动作滤波、改 Kp/Kd 或缩小 action scale，它们会改变训练与实物之间的对应关系。

## 4. 站立正常后，再试一点前进速度

保持同样的地面、供电和防坠条件，使用固定速度，便于比较两次测试：

```bash
.venv/bin/python deploy.py stand \
  --port /dev/ttyACM0 \
  --i2c-address 0x6a \
  --duration 3 \
  --stand-ramp-seconds 12 \
  --policy-ramp-seconds 3 \
  --vx 0.05 --vy 0 --wz 0 \
  --max-speed 5 --print-rate 1 \
  --arm-ground-test
```

这次目标前进速度为 0.05 m/s，速度指令会逐渐增加。三秒窗口主要用来观察起步；确认过程正常后，再逐步延长测试时间。

低速下没形成步态，也是一条需要记录的结果。先看实际 command、动作和机体响应，必要时回到仿真对照；不要因为它暂时不走，就连续加大速度直到突然冲出去。

## 5. 固定指令测试顺利后，再用键盘

在树莓派的真实终端或合适的交互终端里运行：

```bash
.venv/bin/python deploy.py keyboard \
  --port /dev/ttyACM0 \
  --i2c-address 0x6a \
  --stand-ramp-seconds 12 \
  --max-speed 5 --print-rate 1 \
  --arm-ground-test
```

它会在站立过渡后以零 command 开始，默认运行到你退出。

| 按键 | 效果 |
| --- | --- |
| W / S | 前进 / 后退，±0.20 m/s |
| A / D | 左 / 右转，±2.00 rad/s |
| X 或空格 | 行走命令归零 |
| Ctrl+C | 退出并执行停机处理 |

**按键指令会保持，松开按键不会自动停。** 按相反方向会先将该轴归零，再按一次才切换到反方向。X 或空格只是把 command 变成零，策略仍在运行；Ctrl+C 才是退出。

键盘档位比前面的低速测试更大，而且没有固定指令入口的三秒速度过渡，因此留到后面再试。头部 command 在当前入口中固定为零。

## 6. 自己训练的策略，怎样放进来？

先完成训练篇里的接口、数值一致性和闭环验证，再把新 ONNX 复制到树莓派部署目录下的 `teleop/scripts/models/`，保留原文件作对照。

真机的 `stand` 和 `keyboard` 入口可以通过下面这个参数显式选模型：

```text
--onnx teleop/scripts/models/my_walk.onnx
```

把这一项加到已验证的启动命令里，先回到短时零速测试。新模型仍需通过运行入口的 metadata 和控制接口校验；若不匹配，回查训练与导出，不删校验来强行运行。

`deploy.py check` 只检查默认内置 ONNX 和它的 manifest，不能证明 `my_walk.onnx` 已通过验证。替换默认文件还会涉及配套 manifest 的更新，因此第一次尝试新策略更适合保留独立文件名。

## 7. 出问题时，先把这次现场留下来

日志通常位于部署目录下：

```text
teleop/scripts/logs/real_imu_s288_v0_backlash_dr_rotor_pd_m1/
```

CSV 会记录策略输入输出、关节目标、rotor/OutPos、速度、IMU、电压和时间信息；异常停机时还会保存 abort snapshot。日志里有 OutPos 不代表策略在使用它，当前输入仍是 rotor。

排查时按现象回到最近一步：

| 现象 | 先回查什么 |
| --- | --- |
| 读反馈就超时、CRC 或 ID 错 | 电源、地址、线束、通信板，以及是否有另一个进程占串口 |
| 站立过渡就明显扭向错误方向 | 电机对应关系、q=0 参考、direction、机械安装 |
| 过渡正常，策略接管后明显异常 | 模型版本、IMU 轴向、归一化、反馈来源与运行参数 |
| 动作时掉线或电压异常 | 动态电压、接头、供电与总线时序，结合日志看发生先后 |
| 触发超速或倾斜保护 | 保存停机前状态，检查具体关节和动作，不先放宽阈值 |

把启动命令、ONNX 哈希、标定版本、供电方式、防坠状态，以及“在哪个阶段发生了什么”写在一起。比如“站立过渡正常，RL 接管后右膝连续抖动，两秒后超速停机”，就比“上机失败”更容易继续分析。

做完第一轮后，可以记录它实际站了多久、能否起步、转向是否稳定、有没有摔倒。教程和策略都要以这些观察为依据，能站住一小会儿和能可靠行走，是需要分别验证的结果。
