# 故障排查

排查时先保留原始日志和完整启动参数，再按“模型—观测—目标—执行器—整机”顺序定位。一次修改多个层次会降低对照价值。

## 1. 安装与路径

| 现象 | 检查方法 |
| --- | --- |
| console script 报错误解释器 | 重新创建虚拟环境，使用 `python -m` 入口 |
| 导入了另一份训练源码 | 检查 `mjlab_microduck.__file__` 和当前虚拟环境 |
| Pi 缺少 onnxruntime/serial/smbus2 | 在部署 `.venv` 安装运行依赖 |
| 串口不存在 | 检查 by-id、USB 枚举和控制器供电 |
| 串口权限不足或被占用 | 核对设备权限并停止其他标定/运行进程 |

## 2. 模型拒绝加载

先运行 `deploy.py check`。维度、contract 或 HOME 不符通常意味着模型和入口不匹配；哈希不符可能是重新导出后 manifest 未更新。

应同时确认 task、checkpoint、ONNX 来源和归一化。相同网络层数并不表示观测语义相同，不应删除 loader 校验以绕过问题。

## 3. 进入 RL 后姿态偏移

依次核对：机械舵盘安装、模型 q=0 标定、direction、HOME、策略 q 来源和目标坐标映射。头部偏转既可能来自真实负载，也可能是零位或映射错误，不能只调整 Kp/Kd。

特别检查是否误将 OutPos 作为 q，或在纯 rotor 目标路径中叠加了首次 OutPos/rotor 差值。日志里命名为 `motor_position_rad` 的历史字段不能自动当作原始转子位置，应查看 raw 字段和实际赋值源码。

## 4. short_frame、CRC 或 ID 错误

检查电机端动态电压、线缆、连接器、控制器、总线拓扑、重复 ID 和端口占用。将错误按电机 ID 与发生时间统计，比较是否集中在特定动作或负载下。

电压下降可能使通讯和执行器能力同时恶化，但不能仅凭报错类型认定供电是唯一原因。应结合电压时间序列和外部测量。增加容错次数会改变安全行为，不是首选诊断方法。

## 5. q 抖动但 qdot 很小

确认两者来自同一机械侧：本配置应为 rotor q 与协议 rotor speed。输出端运动可能受间隙、柔顺或传感误差影响，不能假设 `d(OutPos)/dt` 与协议速度必然一致。

比较 raw rotor、raw OutPos 和各自时间戳，再讨论滤波或动力学。直接把 qdot 换成输出端差分会改变幅值、噪声和延迟，需要训练与部署同时考虑。

## 6. 超速停机

`--max-speed` 是反馈速度阈值，不是让目标平滑的工具。先比较 action、target step、rotor q/qdot、IMU 与停机原因，不通过调高阈值判断策略是否稳定。

若同一 target 在仿真与真机产生明显不同响应，可做不运行 policy 的 real-target replay。若 target 已经先分叉，应继续检查输入观测及整机状态，不能只归因于执行器。

## 7. 站立正常但起步失败

零速度稳定只验证准静态附近的一部分链路。起步还包含支撑切换、接触、惯量和动态执行器响应。

对照时保持相同模型和 command 曲线，记录真实收到的 vx；分别检查 gyro/gravity、rotor q/qdot、target、反馈力矩和电压。仿真随机推力、不同初始化或不同速度 ramp 都会影响结论。

## 8. 提交可复现问题

建议附带：代码版本、task、模型 SHA256、完整启动参数、电机与供电配置、操作系统、CSV、abort snapshot，以及是否着地、支架是否承重。

机械零位是单机数据，不能要求其他机器人直接套用同一标定文件。共享日志前应移除无关个人路径和网络信息。
