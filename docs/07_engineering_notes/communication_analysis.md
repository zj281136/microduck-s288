# 通信故障、线束与供电排查经验

## 1. 问题背景

S288整机控制需要逐电机发送命令并读取反馈。动态动作时可能出现short_frame、CRC错误、timeout或ID不匹配。症状发生在负载增加后，并不能直接说明是控制增益引起。

## 2. 需要区分的假设

| 假设 | 应查看的证据 |
| --- | --- |
| 动力供电下降 | 电机端电压与动作/错误的时间关系，必要的外部测量 |
| 线束过长或布线问题 | 分段长度、拓扑、同条件短线对照 |
| 接插件接触问题 | 错误是否集中到特定支路、替换前后记录 |
| 控制器/调度 | 请求顺序、TX/RX、循环超时、包龄 |
| ID或串口占用 | 反馈ID、重复ID、其他进程 |
| 闭环振荡导致负载上升 | action、target、qdot是否先于掉压/通信错误放大 |

## 3. 已有证据范围

驱动明确记录通信失败类型；部署日志还包含反馈、目标、电压和时序。原项目中已将USB控制器、电源和线束作为排查项。

## 4. 有效对照方式

比较时保持相同供电、姿态/负载、请求频率和电机ID顺序。一次只改变线束长度、接头、拓扑或电源中的一个因素，记录请求数、有效回包、错误类型、延迟分位数及电压。

短时probe成功只能证明这些请求收到反馈，不表示长期运行零丢包。接口和电源改变后应重新记录条件，不能沿用原“可靠”的结论。

## 5. 故障后的处理

停止运动，保留CSV和abort，再根据时间顺序分析。不要先提高容错次数或关闭CRC检查来获得更长运行时间，这会改变原有故障处理行为。

如果软件停机命令无法送达，必须依靠独立动力切断；零增益状态下保护架需要承重。

## 6. 经验总结

通讯、供电、线束和控制闭环是相互作用的系统。看到报错只说明某次协议交互失败，必须通过条件与时序进一步定位，而非反复调Kp/Kd。
